## 1. 版本定位与执行边界

v0.2 是对整条主线的玩法、美术资产、字体、动效和桌面成品体验进行大型改版。玩家从打开 Mac 应用、进入村庄到逐章通关，应持续感到这是同一个完整的古风武侠游戏，同时通过操作理解 GitHub。

本版的工作量应覆盖主线玩法重构、大批量生成并整合数字资产、跨章节资源系统、场景动效和桌面分发。不能把范围压缩成改几个 CSS 变量、生成一张 Logo、添加几个附加小游戏。预计有效代码和独立美术资产明显增加，但不以代码行数、图片导出数量或生图调用次数代替质量验收。

要求分为两类：

- **必须满足的结果**：来自用户明确反馈，如全主线升级、全应用中文字体、真实生成素材、原生应用图标、自然动效。实施者不得自行降级为“可选优化”。
- **本稿提出的设计方案**：逐章玩法组合、经济数值、时长目标、动画时长等，用于具体化需求；待本稿审阅后按验证结果校准。不能把这些建议描述成用户已经逐项确认。

原始需求中普通窗口体验、一致布局、新手引导、通关后自愿赞助、交流邮箱、知识覆盖审计继续有效。本稿覆盖旧文档中与本次要求冲突的方案，例如用原创线稿作为正式场景美术、通过少量支线代替主线升级、固定整页滚动地图等。项目的模拟边界、存档保护和发布授权规则继续有效。

## 3. 视觉总纲与 Taste Skill 使用方式

**设计判断：面向 GitHub 初学者的古风武侠学习游戏，在现有水墨山水、淡彩人物和纸木器物的基础上大幅提升制作完整度。** 保留世界观和美术气质；重做粗糙的控件、布局与玩法呈现。

本稿采用 Taste Skill 的“先审计现有品牌、统一视觉规则、让动效有目的、在真实页面检查”的方法。拟定设计参数：`DESIGN_VARIANCE=5`，`MOTION_INTENSITY=6`，`VISUAL_DENSITY=5`。这些参数用于约束本项目的设计判断，不是已经通过验收的质量分数。

Taste Skill 的通用营销页或图标库建议不覆盖用户本次明确要求：本项目的主体是游戏；指定的场景道具、图标和按钮必须使用生成美术，不能拿“使用了 Skill”作为未交付素材或玩法的理由。

实施前必须形成一份可对照的美术规范，包含：

1. 参考锚点：现有 `jianghu-full-v1.png`、典型章节场景、三位主角及青砚的实际图片。记录应保留的笔触、矿物淡彩、纸感、轮廓和光影；不是只写一句“国风”。
2. 字体角色、文字层级、器物材质、按钮状态、节点状态、对话面板和游戏盘面的统一规则。
3. 同一件生成道具分别放到地图、章节和弹层中的合成样张，验证尺寸、视角、接地、透明边缘与对比度。
4. 明确淘汰：科技感原子图标、塑料质感 3D 宝典、过亮描边、通用大圆角卡片套满全屏、无语义的角框、用几根线拼出的棚架/船/炉具。

风格一致不等于每个页面长得完全一样：保持共同材质、笔触与排版逻辑，章节可以有不同的游戏盘面。真正的牌类玩法可使用牌面，不能把所有玩法都塞进相同的问答卡片。

| 位置｜过程 | 通过标准 |
| --- | --- |

原图 11 对应 Dock。用户所称“菜单栏图标”按这个实际问题验收；如应用另有顶栏常驻图标，也必须统一。当前没有的常驻顶栏功能无需凭空新增。系统原生菜单的文字显示遵守 macOS 规则。

## 5. R02：批量生成真实美术资产，并完成逐项替换

### 5.1 先盘点，再按清单生产

建立“v0.1 旧元素 → v0.2 美术资产 → 实际使用位置”台账。所有截图指出的元素，以及同类元素在其他章节的实例，都进入清单。至少包括：

| 资产域 | 必须覆盖的内容 |
| --- | --- |
| 全局 UI | 地图、宝典、行囊、返回、重试、帮助、设置、主要确认/领取按钮及相关状态 |
| 地图 | 当前标记、完整锁牌、章号印记、已通关印章、地点牌、通行凭证、路程反馈 |
| 场景器物 | 牌楼、案台、书架、船｜车、信箱、炉具、灯笼、通道、容器、机关等当前粗线占位物 |
| 玩法资产 | 牌面｜牌背、筹码、棋盘、连接件、任务信件、证据签、货物、分支竹签、失败与胜利标记 |
| 经济道具 | 铜钱、成串铜钱、银票、通行证、钱袋、领取与消耗反馈所需画面 |
| 转场与动效 | 书页｜书脊｜页角、分层云雾、需要运动的场景局部、机关状态或精灵帧 |

要求不是生成一张包含所有内容的展示图，而是得到能放进游戏、能单独定位、能响应状态的可用资产。

### 5.2 制作和整合流程

每组资产必须经过：参考图和用途约束 → 生图 → 对照场景审图 → 必要时编辑/重生成 → 分层或透明处理 → 尺寸适配 → 接入真实页面 → 检查全部交互状态。

- 尽可能按场景和材质组多轮调用生图能力；不能只生成品牌图标就结束生图工作。
- 生成工具负责正式视觉素材；代码负责点击区域、排版、可访问语义、状态及动画。CSS 可以做布局、遮罩和效果，但不能把指定道具重新画成几何占位物交付。
- 图片作为按钮外观时，文字、热区、焦点与语义仍须可靠；普通按钮标签使用真实文字，避免生成文字错字和按钮不可读。R06 的固定章号牌按其专门要求导出。
- 每类控件交付默认、悬停/聚焦、按下、禁用、选中/成功及需要的错误表现；可以共享同一底材和状态层，不要求每个状态盲目重生成。
- 正式资产入仓库并进入桌面包，记录资产 ID、来源、参考图、生成记录、尺寸、透明通道、锚点、使用场景、状态、文件哈希和验收截图。
- 禁止假透明棋盘格、白边/灰边、漂浮阴影、拉伸、背景视角不符、物件高光与环境矛盾。既看 200% 裁切质量，也看真实尺寸的整幅画面。

### 5.3 规模与完成标准

以全量清单为分母，**指定旧占位元素替换率必须达到 100%**。每章必须有适合本章玩法的专属核心道具，公共按钮可以复用；不能十三章只换文字和颜色。

本稿建议按约 **80～150 件独立生产资产** 预留制作工作量，最终数量由逐章清单冻结。它是生产预算估计，不能用重复缩放、重复文件、未采用候选图或动画帧数凑数。质量与覆盖率不足时，即使超过此数量仍不通过。

交付台账分别统计：已生成、已审美通过、已接入、已实机验收；这四个状态不得混称“已完成”。

## 6. R03：全应用中文字体必须呈现古风

### 6.1 全面覆盖

范围是本项目可控制的全部文字界面：开始页、选角、地图、每章、导航、按钮、NPC 对话、提示、错误、输入框及 placeholder、设置、存档、弹窗、宝典、词条、教学指南、结算、关于、赞助、页脚及保留的兼容页面。

不能只修改标题、Logo、少数页面，不能只给字体变量改名但最终仍回退到现代无衬线中文。中文数字和标点也要检查。

| 文字角色 | 字体方向与使用要求 |
| --- | --- |
| 品牌、章名、大标题 | 有明显笔意的行书或行楷，控制字形复杂度 |
| 地点牌、短按钮、功能标签 | 隶书或清晰的书法字体，强化古风且一眼认出操作含义 |
| 正文、操作说明、错误提示、长词条 | 清晰的楷书或书卷体；正文同样有古风，不回退为现代黑体 |
| 印章、成就等极短装饰文字 | 可少量用篆书或草书；提供可读名称，不能承担唯一的教学说明 |
| 英文 UI 标签 | 与中文协调的古典衬线或印刷气质字体，保留精确的 GitHub 英文拼写 |
| 命令、代码、SHA、路径 | 使用可读等宽字体，防止 `0/O`、`1/l` 混淆；其中中文注释仍检查字形一致性 |

建议形成 3 类中文字体角色和有限的字体家族组合。丰富感来自明确分工，不在同一段文字中随机换字形。不可用难读草书覆盖新手操作说明，也不可为排版缩小正文来强行免滚动。

### 6.2 字体交付与验收

- 选定真实字体文件，核实开源分发/嵌入许可，随应用离线打包；仅依赖某台 Mac 预装的字体名称不合格。
- 建立全路由、全控件的字体使用表；正文建议 16～18 CSS px，关键操作与说明不得小于 14 CSS px，书法字形需要时加大字号。
- 验证动态内容、常用生僻字、中英混排、数字和标点；缺字回退仍保持书卷气质，不出现一段中突然混入现代黑体。
- 在断网 Mac 安装包检查实际渲染字体和截图；字体加载失败必须被识别，不能把声明了字体名称当成加载成功。
- 对照 v0.1 同页截图，普通正文、按钮和弹窗都应有肉眼可见的改变。

外部 GitHub 网站、GitHub 托管的 README 渲染、系统权限弹窗及 macOS 原生菜单字体不由应用控制，不承诺强改系统。应用内呈现的 README 与指南仍在覆盖范围内。

## 7. R04：升级全部主线章节的核心玩法

### 7.1 必须达到的玩法深度

主线中的每章都应有能独立说明的游戏循环：观察局面、选择策略、执行操作、改变局面、收到反馈、调整并达成目标。不能把几个按钮按固定顺序点完称为三消、捕鱼或牌局，也不能把新增玩法藏到行囊里交差。

每章设计卡必须包含：初始局面、玩家目标、可执行动作、规则和约束、可见的状态变化、失败｜撤销｜重试、至少一种重玩变体、知识对应关系、结算奖励、资产表和动效表。

建议全线至少使用 **6 类有实际规则差异的核心机制**；相同机制允许复用底层，但不能连续三章仅更换牌面文字。前几章规则简单，后续逐步增加资源管理、局面判断和多步骤协作；默认不给初学者强制计时压力。

### 7.2 逐章玩法方案（本稿提案，供审阅与样板验证）

下表以当前实际配置为范围，列出完整主线改造方向。不是当前已完成的功能，也不是只能使用这些游戏类型。

| 章与场景 | 拟采用的主要机制 | 玩家做什么，局面怎样变化 | 必须保留的知识因果与美术交付 |
| --- | --- | --- | --- |
| 0 村口路标 | 路牌连连看与寻路 | 观察需求与路牌，用受路径阻挡限制的连线接通目的地；接对后道路亮起，旅人能走到正确入口 | README、Code、Releases、Fork 的用途决定连线是否成立；生成路牌、地形阻挡物、旗帜和通行路引。使用 Fork 的教学路线不代表所有 Clone 都必须先 Fork |
| 1 护身堂 | 护匣防守与请求拦截 | 不同信使带来身份入口或索取信息的请求；玩家分配核验印、保管格和拒绝槽，避免危险请求越过门禁 | Sign up｜Sign in、安全设置、2FA、Passkey、Recovery codes 决定合法处置；只出现凭据类型道具，无真实秘密输入。生成护匣、请求笺、护符和门禁机关 |
| 2 拓印坊 | 订单经营与机器调度 | 为不同旅人需求选拓印机和交付地点，管理有限工位；产物显示归属、所在位置、历史和关联，交错队列形成策略 | Fork、Clone、ZIP 产生不同结果，不能仅贴不同名称；HTTPS｜SSH、Codespaces 进入后续订单变体。生成机器、原卷、副本、装订件和马车 |
| 3 营火工坊 | 接线｜管道机关解谜 | 在正确工位接通材料和火路；看日志定位断点，修复后验证炉火，学会关闭流程 | 目录、Terminal、Node.js、依赖、npm install/npm run dev、localhost 与状态对应；生成炉膛、工具、接头、线缆和日志纸条 |
| 4 藏图阁 | 分层取牌与书架机关 | 从有遮挡的书架取出证据牌，有限托盘要求安排取牌顺序；把“问题与证据”组成合法组合后归档 | Branch、文件｜目录、历史、License、Tag｜Release、可见范围及归属决定归档；牌被移走不代表删除仓库文件。生成多层书架、册页、托盘和印记 |
| 5 集市鉴宝 | 证据组牌与古风桌面对局 | 在有限调查回合中翻看项目证据、识别虚张声势的摊主；用许可证、环境和维护情况证明选择，可在本章对局中选择虚拟铜钱彩头 | Stars 不等于适配或质量；核心判断依据是 Requirements、License、README、维护状态等。生成案桌、项目牌、证据签、银票和钱袋 |
| 6 飞鸽传书 | 街机接件与分流 | 配置接收规则后应对一批移动来信；正确截取与分流降低漏接和噪声，改变规则可见后续事件流变化 | Star｜Watch｜Follow｜Fork 各有职责；通知设置、Issue｜Discussions 对应正确去处。生成信鸽、不同信件、信台和风铃；不因用户提过捕鱼就强塞鱼池 |
| 7 悬赏亭 | 案卷拼图与委托排程 | 从证据碎片拼出可复现的事件，排除重复委托，安排标签、承接人与里程碑；缺关键线索就不能交案 | Issue 的现象、复现、期望，Label｜Assignee｜Milestone、Comment｜mention、协作告示影响案卷完整度。生成告示板、案卷、证据件和指派令 |
| 8 双城驿站 | 多站点运输调度 | 调度本地、origin、upstream 之间的消息与提交，先辨别各站版本再选择获取、整合、推送；有容量/路线约束的可解局面 | Fetch 更新所知远端记录，不能自动改本地工作区；Pull｜Push｜Sync fork 分别改变相应状态。生成站台、货车、版本货件、回执和站名牌 |
| 9 分流竹林 | 路径规划与双线机关 | 创建并切换修复路径，保持主路状态，观察当前分支和 Diff；在不同起始状态下规划安全修改路线 | Branch 是提交上的分支引用，不能教成复制一整个新仓库；未提交改动不宣称天然隔离。生成竹径、分支标记、差异竹签与路径机关 |
| 10 合卷台 | 有限槽叠签与分组提交 | 从叠放修改签中选择相关变更，放入暂存槽，组合合理的一次提交；随后推送并看到远端回执 | 不是凑三个相同英文词；工作区、Stage、Commit、Push 必须是不同状态。生成改动签、暂存案、封卷、印章、提交记录和快递封套 |
| 11 议事堂 | 协作牌局与冲突修卷 | 选择来源｜目标，提出 Draft，针对不同评审意见补充证据或修改；双方冲突内容需要实际合并整理 | PR 方向、Review｜Request changes｜Approve、Resolve conversation、Conflict 由证据和仓库状态决定，不以击败评审者或赢牌替代正确性。生成议事桌、角色意见牌、合卷册和待检查封签 |
| 12 百炼炉 | 连锁机关与流水线调度 | 安排有依赖的 Job｜Step，执行后找出失败日志并修复；观察取消与重跑，再选择正确版本、产物和发行说明完成发布模拟 | Workflow｜Checks、Failed/Passed/Cancelled、Artifact、Tag、Release、Changelog 各有结果；评审｜检查条件满足后才执行对应合并或发布。生成分层炉具、状态火苗、日志卷、产物箱及发行卷 |

Fetch 与 Pull 的教学界限参考 [GitHub 官方说明](https://docs.github.com/en/get-started/using-git/getting-changes-from-a-remote-repository)；Fork 关系参考 [Forks](https://docs.github.com/en/pull-requests/reference/forks)；评审与合并参考 [Pull requests](https://docs.github.com/en/pull-requests/reference/pull-requests)；流水线参考 [GitHub Actions](https://docs.github.com/en/actions/get-started/understand-github-actions)。上表的古风玩法是产品设计提案，不是上述来源给出的游戏方案。

### 7.3 必须达到的样板深度：第 10 章“合卷叠签”

本样板用于明确“升级玩法”的工作量，其他章节也要提交同等完整的规则说明。

1. **局面**：桌面叠放 8 张改动签，部分被遮挡；本轮任务明确 3 张相关改动，另外有重复证据、无关改动和不应纳入的修改。暂存案有 4 个可见操作槽。
2. **策略**：玩家安排取签顺序并保留必要操作空间，检查差异后决定纳入、退回或先暂存；不是点击系统已写好的“下一步答案”。
3. **教学状态**：移到暂存案表示选定的内容进入 Stage；此时本地历史与远端都未改变。封卷产生 Commit；再交驿站才完成 Push。牌的收拢动画不表示原文件消失。
4. **错误与修复**：混入无关改动时显示具体差异与原因，允许退回该签；暂存后又编辑时显示工作区与暂存版本不同。不会扣掉已完成章节。
5. **目标**：有效提交包含本轮指定相关变更，提交说明有实际含义，远端收到对应提交。本轮恰有 3 张相关签是关卡设置，GitHub 并没有“三张才能提交”的规则。
6. **复玩**：改变遮挡、摆放、任务文件和无关变更，规则保持可解；玩家需要迁移判断，而非记住按钮位置。
7. **反馈**：生成的改动签、案台和封卷产生移动、压印、收卷与回执动画；始终可查看工作区｜暂存｜历史｜远端的状态对应。

连连看、叠牌、斗蛐蛐、牌九、捕鱼等候选只有在“操作本身能够表达该章知识”时采用；不能只把术语贴在皮肤上，也不能把传统游戏输赢误当知识掌握。可借鉴通用规则，不复制具体产品的品牌、关卡、美术或特定角色。

### 7.4 知识与时长验收

- 全部主线保留 P0 与 P1 术语覆盖，并逐条补齐“知识 → 必须做的动作 → 可见结果 → 迁移检验”。只在说明中出现术语不算玩法覆盖。
- 每章至少设计一次能暴露常见误区的局面和一次变体检验；不新增十三套相同的强制问答框，优先把检验放入游戏局面。
- Git/GitHub 的知识是可扩展范围，不宣称有限章节覆盖“全部 GitHub 知识”。区分核心入门、拓展与未纳入范围。
- 建议首次主线游戏时长目标为 90～150 分钟，前几章约 3～6 分钟、后续约 7～15 分钟，最终以真实试玩中位数调整；外部 GitHub 自我练习另计。禁止靠读长文、等待动画、强制刷钱或重复无变化操作凑时长。
- 趣味性不能只用通关率判断。记录新手主动继续意愿、重复玩法疲劳点、失败原因、请求提示次数与操作知识是否能迁移。

## 8. R05：主线贯通的铜钱、银票和通行证

### 必须交付的机制

| 对象 | 获得与用途 | 不允许的替代 |
| --- | --- | --- |
| 铜钱 | 主线章节首次有效完成发放；在后续章节进行有实际作用的消耗，例如购买额外非必需线索、玩法辅助或参与本章虚拟彩头 | 只有“铜钱 +10”文案，没有余额、使用场景或持久化 |
| 银票 | 与铜钱表达同一虚拟财产；通过钱庄兑换或整笔结算获得，使用时扣减同一余额，避免双算 | 只在行囊展示一张永远用不到的图片 |
| 通行证｜路引 | 从满足学习条件的主线节点获得，在后续关卡核验和展示；明确发放者、用途与解锁关系 | 用钱直接买通关、跳过知识条件，或只有一个无用途徽章 |

**首轮可调数值提案**：首次通关奖励 10 铜钱；本章迁移检验首次通过另奖 5；100 铜钱可换 1 张银票；额外线索 5 铜钱；鉴宝桌彩头为 0｜5｜10 铜钱。数值需要经济模拟和试玩校准，不是已经确认的平衡结果。

- 第 0 章结束就看见路引和钱袋；进入前半程时至少实际使用一次资源功能。兑换可在较后章节出现，不为了看到银票强制刷钱。
- 鉴宝桌等对局属于主线章节内部，可选择无彩头继续；现金赞助与游戏货币无关联，无充值、提现、转让或现实收益。
- 彩头结算规则在开局前可见，损失最多为本轮投入；知识判断错误不能靠随机获胜判定通关。余额不足仍可完成主线，免费教学提示永远可用。
- 记录收入、支出、兑换、来源章节与余额；刷新、撤销、重放、导入存档不重复发放首次奖励，不出现负数和双重扣款。
- v0.1 存档升级后保留已完成主线；补发规则确定且幂等。老玩家可从复习入口体验新玩法，不被强迫丢档重玩。
- 所有钱币、银票、票据、兑换容器和通行凭证按 R02 制作为真实美术资产，并有领取、使用和不足的视觉反馈。

## 9. R06：地图锁与章号采用完整美术节点

未解锁节点必须看起来是地图里的真实物件，例如被铜锁扣住的木牌、封缄卷轴或门楼路引。实施前先做两种构图合成比较，选定一个体系推广。

**正式交付内容：**

- 锁体、连接结构、承载章号的实体牌面｜封签、章号印记和接地关系组成完整节点。
- 每章交付经校验的节点图片或完整美术层组合，章号与器物在视觉上是一体。可使用生成底材加经校验的书法数字合成导出 PNG｜WebP；不是在通用锁图标下面再挂一行裸数字。
- 生成的字形必须人工校对。固定章号图片可用已授权书法字形修订后导出，不能保留错误数字、乱码或错序。
- 未解锁、当前可进入、已完成、解锁中四种状态有完整表现。共享材质允许复用，但章号、锁态和当前状态可辨认。
- 锁定原因与地点全名通过悬停、焦点或点选说明呈现；可访问名称由真实文本提供。不得只靠颜色或不可读印章传递状态。

**直接不通过的情况：**原锁图标外围加方框｜圆角框；仅加阴影；裸数字仍飘在锁下面；复制一张与地图光影不符的巨大铜锁贴满地图。地图缩到目标普通窗口尺寸后仍须美观、清楚且不遮挡关键地形。

## 10. R07：场景驱动的动态系统与章节翻页

### 10.1 逐场景设计，不按关键词堆动画

每个章节和地图都必须有动效设计表，记录：发生位置、场景依据、触发条件、参与图层、视觉层级、时长｜循环、遮挡范围、性能策略、减少动态效果版本。

| 动效层级 | 设计内容 | 必须满足的条件 |
| --- | --- | --- |
| 环境生命感 | 水流、岸边反光、雾层、灯火、衣摆、炊烟、鸟群等合适候选 | 先找到实际水面/植物/灯具等来源；允许某场景没有环境循环动画 |
| 操作反馈 | 翻牌、拖放落位、叠签、压印、装车、投信、机关开合 | 对应玩家动作、命中状态与物件材质，重要状态可清楚观察 |
| 叙事反馈 | NPC 接物、路引核验、钱袋收入、奖励交接 | 推动当前任务，不能只是与学习无关的庆祝特效 |
| 全局转场 | 书页翻动、地图散雾、地点亮起、沿路移动 | 保持进度和空间关系，不能越过地图解锁过程或丢失存档 |

- 水纹只作用于实际水域的透视和遮罩内，不覆盖岸边或室内案台。落叶从存在的树冠附近产生，数量与风向自然，不让一张叶子机械地横穿所有页面。
- 云雾要有云团形态、前后层次和适度移动；解锁表现为该区域雾团舒展/消散，而不是一块矩形渐变平移。
- 炉火跟随点火、失败、修复和成功改变；信鸽有出发、飞行、落台的完整关系；牌面落位有符合纸木重量的反馈。
- 需要的独立图层、纹理和关键帧纳入生成资产清单；可用骨骼、网格、遮罩、粒子或逐帧驱动，不要求每帧都生图。不能用粗线条动画补回被要求替换的道具。

### 10.2 翻书转场纳入正式设计

章节切换采用“武林游记翻页”的统一叙事方式，至少制作一种可运行的样板供验收：

1. 章节结算完成，先可靠保存状态和奖励。
2. 玩家确认返回地图时，当前章节作为书页翻过，显示江湖地图；对应节点散雾并展示下一站。
3. 玩家进入下一章时，再展开该章场景页。不能用翻页自动跳过地图或越级通关。
4. 建议单次 0.6～1.2 秒，可跳过；书页层级、页背、纸纹和弯曲｜遮挡必须完整，不用整屏简单水平位移冒充翻页。
5. 减少动态效果时改为短淡入或直接切换，结果一致；动画中刷新、关闭或连续点击不会重复奖励、留下黑屏或锁住输入。

动画覆盖验收是“每章关键动作和转场有恰当反馈”；不是“每章必须飘叶子”。需要录制正常速度视频审查，静态截图或 CSS 中存在 keyframes 不算动效完成。

## 11. R08：普通窗口完整可玩，同类页面保持一致

- 以实际可用内容视口设计，并分别记录窗口外框、系统标题栏和 Web CSS 尺寸。测试内容视口 1440×900、1280×800、1024×720，以及当前桌面配置的默认与最小外框窗口；不把 Retina 像素或截图尺寸误当 CSS 像素。
- 在支持的普通桌面窗口下，地图、当前目标、主要入口同屏；章节的目标、场景核心交互、必要操作与即时反馈同屏。
- **禁止**通过 `overflow:hidden` 把内容裁掉，删除必要说明，隐藏声明，极度缩小字体或把主操作藏到内部滚动底部来制造“无滚动”。元素存在于 DOM/可访问树，不代表用户看得见、点得到。
- 长宝典、完整日志和历史证据允许在明确的阅读面板内滚动；默认完成本章必需的按钮不依赖翻找滚动区域。
- 行囊、宝典、教程使用合理的抽屉/对话面板或独立阅读视图；关闭后恢复原场景。返回地图不能把展开的行囊继续堆在地图上方。
- 同一视口下各章共享稳定的导航、章标题、场景区域和操作区域尺寸；切章后场景区域宽高及上边缘不因本章文字长短跳变。内容变化在内部设计解决。
- 背景保持比例与明确相机区域，禁止横纵分别拉伸；人物接地、物件比例和主要地平线有规范。地图不能因缩放漏掉已配置的地点。
- 游戏盘面可因玩法不同改变内部结构，不能为追求一致而把运输、连线和牌局强塞为相同卡片。
- 小于支持尺寸或用户大幅放大文字时允许可控的阅读退化，保证内容可达；不能剪裁任务或宣称已满足普通窗口标准。

验收证据包含同尺寸的相邻章节对照截图、窗口调整视频、实际点击｜键盘操作和边界检测。截图中被遮挡的主按钮是缺陷，即使编译和测试通过也不能交付。

## 12. R09：每章新手引导随玩法重写

新增游戏规则必须配套新增教程，不能复制同一句“看目标、做操作、验结果”覆盖十三章。

- 首次进章用简短目标说明交代“为何来到这里、怎样赢、对应哪件 GitHub 事”。
- 用真实可交互局面的第一步教学，演示一次关键动作，然后让玩家做一次；演示不代替玩家通关。
- 首次失败立即指出哪个规则与知识发生冲突，保留局面，提供撤销和分级提示。
- 玩家可随时重看规则，离开宝典后回到同一局面；默认全中文帮助，英文原词伴随出现。
- 鼠标拖放提供点击和键盘替代；牌面遮挡、颜色和动效不能成为唯一信息源。

建议至少邀请 5 位没有 GitHub 基础、未看过本项目的人进行首轮走查：至少 4 位能在 60 秒内找到第一步，并在默认帮助下完成前三章，无旁人口头教学。该小样本仅用于发现问题，不作为统计学上的普遍掌握率证明。

## 13. R10：通关后的古风答谢、联系与赞助

- 全主线通关并完成相应结算后出现“江湖留笺｜茶资随缘”入口，普通继续/复习入口仍清晰可用。
- 赞助面板使用与主界面一致的茶案、信笺或功德簿美术，文案朴素，例如“若这段江湖路于你有益，愿意的话，可留一盏茶资，助此书续写。”不得自动弹出催付、金额排名或付费通关暗示。
- 接入用户指定的**支付宝收款码和阿里巴巴商家收款码**；不把第二项擅自改成微信二维码。实施时确认维护者所提供的文件与渠道名称一致。
- 真实二维码由维护者提供，不使用生图伪造二维码，不改绘码区；背景装饰在码区和留白之外，真机扫码核对显示对象与渠道。
- 当前未提供这两张真实资产，收款功能保持禁用，但界面、配置、状态与通关入口仍须完成。验收状态写“真实收款码接入待素材”，不能写成全部赞助需求完成。
- 交流邮箱使用 `603244647@qq.com`，放于关于、通关留笺等合适位置，支持复制；桌面环境应实测复制或邮件入口，不只写一个可能被协议拦截的链接。
- 赞助与游戏铜钱｜银票完全分离，不能购买通行证、改变评价或影响毕业。

## 14. 参考研究与实现组织

本轮不把“当下热门”当成未经验证的事实。后续玩法预研可从已有 `docs/research/GAME_AND_ASSET_REFERENCES.md` 继续，也可重新检索，但应为每个采用方向记录：参考链接、观察日期、具体可借鉴规则、与本章知识的联系、技术适配和许可边界。

参考结果必须落实到设计决策，不能只列 GitHub 链接或装一个 Skill。现有 Next.js/React/Electron 的可行实现优先；需要专用游戏渲染/动画库时，用样板的性能与交互证据决定，不能为“显得大型”盲目更换技术栈。

资源可按共享控件、章节专属、角色、动效分包；采用合适压缩、多尺寸和按章加载。桌面断网运行时不得依赖远程图片、字体或在线生图。

本版调整进度模型时继续使用版本化存储。新旧存档转换、章节 ID、奖励账本、设置、导出/导入和中断恢复要作为正式工程工作，不留到最后临时补丁。

### 15.2 工程验证与质量结论

必须运行项目规定的 `content:validate`、`content:coverage`、`typecheck`、`lint`、`test`、`build`，并检查资产、桌面构建/打包、协议、安全边界和持久化。对新玩法状态机、奖励幂等、存档迁移、不可解局面及转场中断补充有意义的测试。

这些检查证明工程层面的特定性质，**不证明生成素材已替换、玩法有趣、按钮实际可见或整版符合审美**。自动化受环境限制未跑通的项目如实标记；可以补充直接实机证据，不能将未执行的测试改称通过。

交付报告必须按 R01～R10 分别标注“完成且有证据｜未完成｜等待外部素材”，列出剩余工作。只要仍有主线章节未改、占位资产未替换、必要按钮被遮挡或原子图标残留，就不能宣称“v0.2 全部需求已完成，仅待用户审美”。

签名、公证、平台覆盖与上线批准分别记录。用户对具体包人工核验通过后才允许发布；候选包须明确标识 v0.2 及构建版本，不能继续用 v0.1 文件名混淆版本。
