## 1. 先看结论：这次要改成什么

从“带游戏化包装的 GitHub 题库”，改成“下载即玩、沿江湖地图推进、通过实际操作学习 GitHub 的桌面冒险游戏”。

**Design Read：面向电脑上的中文 GitHub 新手，用淡彩水墨的江湖地图建立探索感，用清晰的现代文字和操作区承载学习；武侠负责故事与记忆，真实 GitHub 概念负责能力迁移。**

核心体验：

1. 在你的 GitHub 仓库首页找到对应电脑的下载按钮，下载成品应用并打开，不需要先安装 Node.js。
2. 选择男侠客、女侠客或练功小猫，收到修复《江湖夜行图》的委托。
3. 在真正的空间地图上移动，完成一个场景任务，驱散通往下一处地点的迷雾。
4. 鉴宝、整理驿站、制作分支、审阅卷宗等任务各有操作对象和规则，不再每关只答一道选择题。
5. 英文术语随使用进入“武林宝典”；最终回到真实 GitHub，在自己的 Fork 内完成贡献练习。

不做：大型开放世界、即时战斗数值养成、联网多人、账号系统、付费关卡、抽卡、体力、强制分享、强制 Star、复杂技能树。

## 2. 需要你审核的关键决定

| 编号 | 建议默认方案 | 意味着什么 |
| --- | --- | --- |
| D1 入门顺序 | 先下载成品体验，再完成真实 Fork、Clone、源码运行任务 | 不再要求第一次进入游戏前先配置开发环境；完整毕业仍保留真实实操 |
| D2 运行方式 | 独立桌面应用；优先验证 Electron 封装现有前端 | 用户打开应用，不是解压源码后双击 HTML，也不是先启动终端 |
| D3 平台范围 | Windows 11 x64、macOS Apple Silicon 为首批验收目标 | Intel Mac、Windows ARM、Linux 后续按实机能力增加；不承诺未经测试的平台 |
| D4 游戏形式 | 2D 江湖地图＋分场景小游戏＋连续主角剧情 | 不是三维大世界；不靠换背景和按钮名称冒充小游戏 |
| D5 美术路线 | 原创淡彩水墨武侠，三个角色共用课程和难度 | 人物核心素材原创；有明确许可的代码、通用素材可择优改编 |
| D6 设备重点 | 桌面游戏优先，不建设完整手机游戏工作台 | 手机只保证项目介绍、下载说明和分享图可读；竖屏视频不等于移动端产品 |

这些建议可以整体批准，也可以按编号修改。其中 **D1 是对最初“先 Fork/Clone 才能开始”的明确调整，必须审核后才能落地**。

## 3. 当前实现与目标的差距

以下是本轮仓库静态检查所得，不代表已经重新执行整站验收。

| 当前实现 | 问题 | 本轮修改方向 |
| --- | --- | --- |
| `src/app/map/page.tsx` 使用章节卡片列表 | 没有空间关系、角色位置、迷雾；各章入口都指向 `/play` | 有坐标和路径的地图，点击地点进入对应关卡 |
| 任务工厂为每章生成一道 options 题 | 不同章节缺乏不同玩法 | 独立任务类型、多个操作步骤、场景状态与目标判定 |
| reducer 可直接选择任意章节 | 不能形成逐步解锁 | 先修条件由核心状态机校验，不能只把按钮画灰 |
| 正确回答可给该题关联的一组 P0 记掌握 | “词条被引用”不等于“能力已验证” | 按操作证据与迁移测试分别记录掌握情况 |
| 主要按 Next.js 开发服务器运行 | 普通下载者还需 npm 和开发环境 | 桌面发布包与开发者源码包分离 |
| 有品牌插图，但没有统一角色资产系统 | 连续主角难以贯穿地图与任务 | 角色设定、表情、动作、场景资产及动画规则统一管理 |

现有课程覆盖报告只能证明其对应校验规则下的数据覆盖，不能直接用作新小游戏的教学效果证明。改版后需要重新审查课程内容和通关证据，不能继承“旧存档即全掌握”的结论。

## 4. 用户入口：一个按钮下载，打开就能玩

### 4.1 两条入口，面向不同用户

**普通玩家主入口：**

GitHub 仓库 README → 选择系统下载 Release 成品 → 安装/解压并打开 → 选择角色 → 开始游戏。

**源码学习入口：**

GitHub 仓库 README → 中文 START_HERE → 登录官方 GitHub → Fork → Clone 自己的 Fork → 安装 Node.js → `npm install` → `npm run dev`。

两者是同一个课程产品的不同运行方式。必须明确区分：

- 下载成品应用：获得可以运行的游戏，不等于 Fork 或 Clone。
- `Code → Download ZIP`：获得源码快照，不等于已经安装应用，也不是完整 Clone。
- `Releases → Source code (zip)`：GitHub 提供的源码归档，不是面向新手的桌面安装包。
- Fork：复制仓库到自己的 GitHub 账号；Clone：把仓库及 Git 历史带到工作环境。

公开仓库的成品下载不以 GitHub 登录为前置条件。登录仍只发生在 GitHub 官方网站或 GitHub Desktop 中。

### 4.2 README 首屏要求

在大量说明、徽章和目录之前展示以下信息结构。这里是文案线框，不是已经可点击的发布链接。

```text
GitHub 新手村
用一场武侠冒险，学会 GitHub。

第一次来？先下载游戏，不用先安装编程工具。

[下载 Windows 版]  [下载 Mac Apple 芯片版]
[不知道选哪个？]  [全部版本 / 下载失败帮助]

1. 点上方按钮下载适合自己电脑的应用。
2. 按安装说明打开应用，选择角色开始。
3. 跟随剧情，之后再学习真实 Fork、Clone 和 Pull Request。

想直接学习源码？[从这里开始：Fork、Clone、运行 →]
```

下载入口下补充文件类型、适配系统、版本信息、成品与源码包的区别。GitHub README 不能自动判断访客系统，因此使用清楚的分平台按钮，不伪造“自动识别电脑”的效果。

正式发布后，按钮可使用 GitHub 支持的固定资产名直链，例如 `.../releases/latest/download/<asset-name>`，并保留 `.../releases/latest` 作为备用入口。每次正式发布必须提供约定名称的对应文件，不能留下失效按钮。[官方依据](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases)

### 4.3 本地应用体验要求

- 首次体验无 Node.js、npm、Git、终端和开发者环境前置条件。
- 下载后的安装/解压步骤按系统分别说明；“一键下载”不承诺绕过系统安装和安全确认。
- Windows 候选提供安装包；macOS 候选提供 DMG。便携包是否增加，由打包验证决定，不能让用户面对无说明的多个相似文件。
- 字体、角色、场景、动画、课程、音效随包提供。断网可玩全部模拟课程；真实 GitHub 操作与官方外链需要网络。
- 默认手动从 Releases 更新；本版不做后台自动更新或遥测。
- 不把真实 GitHub 登录页嵌入游戏 WebView。需要实操时打开系统浏览器，游戏明确显示“前往真实 GitHub”。
- 本地进度可导出、导入、清空；更新应用不能主动清除进度。桌面版和浏览器开发版不承诺自动共享存档。
- 发布说明含文件校验值、已验证系统、已知问题及卸载/保留存档说明。

签名、公证与操作系统安全提示属于正式分发工作，不能仅靠打包宣称解决。需要维护者证书或账号时另行取得授权；不指导用户关闭系统整体安全保护。[Electron 分发说明](https://www.electronjs.org/docs/latest/tutorial/application-distribution)

### 4.4 保留完整教学闭环，但不堵住第一次体验

第 0—3 章采用“游戏练习＋真实出村任务”双栏记录：

- 游戏部分完成后可以继续探索，不因为尚未安装 Git 而失去继续学习的机会。
- 真实登录、Fork、Clone、源码运行可当场完成，也可暂存到“出村历练”。
- 出师前必须回看并逐步自查这些真实任务，以及自己的 Fork 内的毕业 PR。
- 进度区分别显示“模拟课程完成”“知识能力达标”“真实操作：玩家自述完成”，绝不合并显示成“GitHub 已验证”。
- “源码运行”不因已打开桌面包而自动打勾。推荐 Desktop＋本地路线；Codespaces 是可选远程环境路线，须标明不等同于本地 Clone，并说明额度可能受限。
- 如用户仅想玩游戏，可获得“模拟冒险完成”结果；不能因此获得措辞含真实贡献完成的出师结果。

## 5. 真正的江湖地图与迷雾系统

### 5.1 地图不是章节列表的背景图

地图由可辨认的山、水、桥、集市、驿站和山门构成。每个章节是一个有位置、有场景标识的地点，路径连接实际的先修关系。采用原创 2D 斜俯视插画，不要求自由寻路或复杂碰撞。

建议空间结构：

```text
入谷营地                   江湖集市
0 村口 → 1 护身堂          4 藏图阁 → 5 鉴宝集 → 6 飞鸽台
           ↓               ↑                        ↓
        2 拓印坊 → 3 营火台                  协作山门
                                      7 悬赏亭 → 8 双城驿站
                                                     ↓
百炼盟会                                  10 合卷台 ← 9 分流竹林
11 议事堂 → 12 百炼炉 → 13 藏经院                ↓
       ↑_________________________________________|
                     ↓
              出村历练与出师峰
```

图示仅说明节点归属与学习顺序；正式地图布局需按可读路径重新绘制。四个区域是新的地图分区，不改变课程“认识、协作、真实实践”的目标。

### 5.2 地点状态

| 状态 | 画面 | 用户能做什么 |
| --- | --- | --- |
| 未解锁 | 淡墨迷雾、建筑剪影、锁定缘由 | 查看名称及前置任务，不进入主线挑战 |
| 可进入 | 迷雾散开、路标亮起、路径显现 | 点击/键盘确认进入 |
| 进行中 | 主角驻留、阶段进度标记 | 从最近保存的操作步骤继续 |
| 已完成 | 地点恢复生机、印章标识 | 复习、重玩，不抹掉历史完成记录 |
| 待真实实践 | 独立的出村路标 | 打开指南和自查清单，不伪造外部状态 |

规则：

- 第一次开始仅开放第 0 章；完成当前模拟关卡后解锁下一章。真实待办按第 4.4 节管理。
- 解锁条件来自关卡目标与依赖图，不来自点击次数、播放动画结束或章节数组下标。
- 迷雾不能遮住当前目标、返回入口、宝典或设置；相邻未知区域保留轮廓，避免用户不知道去哪。
- 主角沿短路径移动到目标地点；动画可跳过，减少动态效果时直接定位。
- 提供“回到当前任务”“缩放重置”，以及同数据驱动的无障碍地点列表。
- 地图、直接路由、任务日志都服从同一解锁判定；不存在改 URL 即正常通关的问题。
- 自由探索允许预览所有场景，但使用独立练习状态，不修改正式主线记录。此模式不是中文辅助等级，应从辅助模式中拆开。
- 演示模式使用固定种子和独立内存存档，允许跳关/重置，持续标记“演示”，不能导出真实毕业结果。

## 6. 主角、世界观与贯穿剧情

### 6.1 主角选择

开局三个候选角色，名称暂定，统一放入内容配置：

| 角色 | 视觉身份 | 一致性锚点 |
| --- | --- | --- |
| 男侠客 · 陆行舟 | 轻装游侠，携卷轴匣 | 束发轮廓、靛青衣带、同一卷轴匣 |
| 女侠客 · 沈知微 | 轻装游侠，携卷轴匣 | 发髻轮廓、赭红衣带、同一卷轴匣 |
| 练功小猫 · 阿团 | 会说话的小猫侠客 | 固定毛色花纹、青色短褂、短尾轮廓 |

三者无能力差异、不改变题目难度或毕业条件。不要用性别绑定“力量/辅助”等职业。小猫不是低龄简化课程，也不能像 Octocat。

提供全身预览、名字和确认按钮；不要求输入真实姓名。默认使用角色名，分享卡也不自动包含系统用户名。可在营地换角色，保持进度。剧情对角色以中性称呼“少侠”适配，猫角色仅有少量不影响教学的表情和台词变化。

### 6.2 同一主角必须出现在四个地方

地图上的行走小人、任务场景内的角色、对话头像、完成/分享画面必须使用同一角色 ID 的资产组合。禁止每关临时生成一个“差不多的人”。

生成顺序为：角色设定表 → 正侧背视图 → 表情表 → 动作资产 → 各场景复用。后续编辑必须引用已确定的角色参考；角色合成与背景分开，避免每次生成整幅场景导致人物变脸。AI 生成不保证天然一致，需要人工式视觉核验、重绘和裁切验收。

### 6.3 故事主线

村里共同维护一本帮助夜行旅人辨路的《江湖夜行图》，虚构仓库仍可使用 `nightwalk-map`。玩家发现 README 把安全入口“南门”误写成“北门”，受维护者委托调查并修复。

前期认识地图与消息规则；中期提交 Issue、建立分支、修正文案；后期通过 Review 与检查，合并并整理发布。每关交付物进入后续剧情，而不是上一关结束就遗忘。

少量固定 NPC：村中维护者、集市鉴图人、驿站信使。NPC 各自有头像、姓名、职责和口吻表。教程说明可回看，长对话可跳过，但关键任务要求始终保留。

武侠意象仅作类比，不宣称“Fork 就是偷秘籍”“Push 就是合并”“Star 就是付费供奉”。GitHub 是协作平台，故事强调公开规则、互助与安全贡献。

## 7. 关卡设计：每关都有可操作的场景

以下是关卡规格的产品层设计。制作时逐条映射现有完整词汇库；表中的术语只是关键示例，不可据此删掉原有 P0/P1。每关必须有“初始状态、目标、可执行动作、状态变化、错误反馈、完成判定、复玩变体”，不能仅把选择题移到插画上。

| 章 / 场景 | 小游戏与实际操作 | 判定与学习结果 |
| --- | --- | --- |
| 0 村口路标 | 在原创仓库导览图找入口，把 README、成品 Release、Code 源码菜单归位，拿到正确的行囊 | 能按“读说明/装应用/看源码”找不同入口；不把 Star 当下载 |
| 1 护身堂 | 整理安全行囊：把凭据留在私人保管区，检查目标域名，拒绝 NPC 的索密请求 | 区分 Sign up/Sign in、2FA、Passkey、Recovery codes；不出现真实凭据输入框 |
| 2 拓印坊 | 操作三张桌面：账号藏书楼 Fork、电脑工作台 Clone、文件快照 ZIP；观察副本与连线变化 | 副本建立在正确位置，能解释 ZIP 为什么没有正常 Git 同步关系 |
| 3 营火工坊 | 在模拟目录与终端中选对项目位置，安装依赖、启动本地页面，再停止服务；修复缺依赖场景 | 分清成品应用与源码运行，理解 Node/npm/localhost；模拟命令不执行真实系统命令 |
| 4 藏图阁 | 探索仓库建筑剖面，打开文件夹、README、历史、分支、许可证与版本柜，按委托找证据 | 对 Owner、Public/Private、main、License、Tags 等能定位并说明用途 |
| 5 集市鉴宝 | 对比摊位上的候选项目卷轴，逐项查 README、环境要求、License、Release、维护线索并放置证据签 | 根据使用需求选项目并说明依据；不以星数高低直接判定好坏 |
| 6 飞鸽传书 | 将收藏、通知、关注作者、创建副本四种委托投到不同机关，预览收件箱变化 | 区分 Star、Watch、Follow、Fork 和 Notifications；Star 可选 |
| 7 悬赏亭 | 根据南北门错误整理现象、复现、期望，检查是否重复，创建 Issue 并整理标签、负责人和里程碑 | Issue 信息足够讨论；识别 Open/Closed、Label、Assignee、duplicate 等；领取委托注明是游戏机制 |
| 8 双城驿站 | 在本地、origin、upstream 三处传递提交信件；Fetch 观察、Pull 整合、Push 上传、Sync fork 同步 | 可视化每次动作改变哪个仓库/分支；含 Desktop 与命令视图切换，不把四者混用 |
| 9 分流竹林 | 建立修复分支、编辑 README、查看 Diff、选择 Stage 范围、写 Commit message、Commit、Push | 分支独立；只有暂存内容进提交；本地提交不自动抵达远程 |
| 10 合卷台 | 把两份卷宗放入 base/head 台座，选分支、检查差异，创建 Draft PR 并送审 | 目标/来源方向正确且变更来自已 Push 的分支；理解 PR 是合并变更提案 |
| 11 议事堂 | 沿变更行阅读 Review，处理 Request changes，补 Commit/Push，再讨论、Resolve conversation 和 Approve；体验简化冲突分歧 | 区分 Comment/Approve/Request changes；旧批准或消除讨论不等于所有检查通过；禁止盲目覆盖冲突 |
| 12 百炼炉 | 观察 Workflow 的 Job/Step，追踪 Failed 原因、修复并重跑；通过 Checks 后由有权限的模拟维护者 Merge，再整理 Tag/Release/Changelog | CI 与 Merge 形成因果顺序；演示不同合并方式、删分支与失败/取消；理解 Pages 不等于任意后端托管 |
| 13 藏经院 | 为项目装配 README、CONTRIBUTING、LICENSE、CODE_OF_CONDUCT、SECURITY 与模板；给漏洞和普通问题选择正确渠道 | 理解仓库治理与角色权限；展示 Discussions、Wiki、Projects 等扩展入口的使用边界 |
| 出师峰 / 真实实践 | 在自己的 Fork 建分支、写练习文件、Commit、Push、创建内部 PR、检查 Files changed、Merge、删分支；回看入门实操待办 | 逐项玩家自查，不收 URL、账号或凭据作为强制证明，不向原仓库制造毕业 PR |

章节 11 与 12 的剧情交付顺序需要微调：11 处理审阅与冲突概念，12 完成检查后执行最终合并。不能为了保留旧标题而演出“先合并、后检查”的错误流程。Checks 通过是本教学项目的推荐合并条件，不宣称所有 GitHub 仓库默认强制采用这一规则。

### 7.1 “集市鉴宝”完整示例

**委托：**为夜行图寻找一个自己电脑能运行、许可适合预期用途、安装说明足够的地图工具。

画面为主角站在集市，桌上三份不同项目卷轴。NPC 交代需求，证据托盘始终可见。

1. 点击卷轴展开该项目资料；不是预先把好坏用颜色告诉玩家。
2. 查看 README 的 Installation/Requirements，比较需要的运行环境。
3. 打开 License，判断当前用途是否需要进一步确认；没有许可证时不默认可任意复制。
4. 查看 Releases、Updated、Archived、Issues 等线索；解释每条线索能说明什么、不能说明什么。
5. 选中资料片段后“收为证据”，证据进入托盘；拖拽或键盘把它放到“环境/使用条件/维护线索”对应栏。
6. 给候选卷轴标注“适合当前委托 / 信息不足 / 不符合当前条件”，交付一个有证据支持的选择。
7. 通关后卷轴盖印，主角收入行囊，地图通向飞鸽台的雾散开。

失败示例：“你引用的是 Stars。它能反映关注度，但不能证明你的电脑满足 Requirements。请查看运行环境说明。”保留已找到的有效证据，立即重试。

判定不是仅点击所有热点，也不只是选择唯一金色卷轴：至少核对环境与使用条件，并作出与证据一致的推荐。变体更换项目条件，避免背答案位置；复杂许可证只做认识和提醒，不代替法律判断。

### 7.2 “分流竹林”完整示例

场景中的竹简路径代表分支，旁边是清楚标注“教学模拟”的文件编辑、Diff 和暂存区。

1. 从 main 建立 `fix/south-gate`，主角移到新路径。
2. 编辑 README 的错误位置；另有无关改动作为识别练习。
3. 查看 Diff，确认只修正目标信息，没有删除周边说明。
4. 选择本次相关修改进行 Stage，观察工作区与暂存区的差别。
5. 输入能说明意图的 Commit message；不强迫背一个固定句子，也不使用 AI API 判分。
6. Commit 后出现提交节点；无关未暂存内容仍留在工作区。
7. Push 后 origin 对应分支出现该节点，upstream 保持不变；随后解锁合卷台。

严格状态校验目标文件内容、分支、暂存集合、提交快照与远程差异。消息检查采用透明规则并说明局限，不能凭字符长度宣称理解了提交语义。

### 7.3 游戏性底线

- 核心是探索、整理、构造、检查和协作，不是反应速度、战斗操作或抽奖。
- 一个任务可以包含少量判断题，但不允许所有章复用同一 options 模板。
- 失败反馈说明具体原因与下一步；保留有效进展，不扣体力，不清空整关。
- 开始时展示目标和预计操作类型；动画、剧情可跳过，教学目标不可由跳过动作直接完成。
- 新手可获得分级提示：指出范围 → 解释概念 → 示范一步。示范动作单独记作练习，不直接计作独立掌握。

## 8. 武林宝典与按钮语言

英文词典升级为贯穿全程的“武林宝典”：按主题、当前场景、已练习/待复习组织，可搜索英文和中文，点击打开官方来源、常见错误与相关练习。

- 学习内容不因地图迷雾锁住。未遇到的术语也可查询，进度只影响“见过/练过/掌握”的标记。
- 默认全中文辅助；保留中英对照、悬停/聚焦解释、挑战提示。英文原词必须能找到。
- 收录动画只是反馈，不等于掌握。已收藏、已遇见、已练习、已通过迁移测试使用不同状态。
- 控件示例：“封存改动 · Commit（提交）”“递交合卷提案 · Pull Request”“查看差异 · Diff”。
- 真实 GitHub 指南中以真实按钮标签为主，不使用只在游戏内出现的武侠名称指挥用户点官网。
- “入门历练、江湖地图、武林宝典、出师记录、支持项目”等用于游戏导航；安全、错误、文件路径等高精确信息使用直接的现代语言。
- 不把正文全部变成古文，避免“吾辈当于远端合卷”这类增加理解负担的叙述。

## 9. 视觉、动画与素材规范

### 9.1 视觉方向

- 色彩：暖纸白承载阅读，墨灰文字，靛青用于当前路径，朱砂用于目标/印章，柔和青绿用于完成状态。错误不能只靠红色区分。
- 地图：淡彩水墨山水与清楚建筑轮廓；操作区使用低纹理纸面。不要把文字直接烘焙到背景图。
- 字体：标题可少量使用有明确开源许可的书卷风字体；正文与英文使用清晰字体、本地随包提供，不全篇毛笔字。
- 按钮：细墨边、纸签或木牌造型，状态与焦点轮廓清楚；装饰不能挤占点击区域。
- 桌面布局：场景操作区占主体，任务目标和 NPC 对话在侧边/底部，宝典可展开。不能仍以巨大任务日志占中心、动画退居背景。
- 暂定最低工作窗口 1024×720，主要设计与录屏验收 1280×800、1440×900 和 1920×1080；空间不足时提示调整窗口，不强行塞成手机页面。
- 风格保持轻武侠而非重仙侠：无需堆满法阵、金边、发光装备和资源条。

Taste Skill 在本轮用于 Design Read、品牌层级与避免装饰压过内容。采用清晰视觉层级、克制配色、统一间距和有理由的动效；不把落地页叙事布局、极简无插画或单一 CTA 规则套进多步骤游戏工作台。地图与玩法以教学可用性和明确状态机为依据。

### 9.2 动画分级

| 类型 | 建议表现 | 边界 |
| --- | --- | --- |
| 日常 UI | 150—250ms 展开、聚焦、证据归位 | 不拖慢连续操作 |
| 地图解锁 | 600—1200ms 迷雾散开、路线上色 | 可跳过，状态先持久化，不靠动画回调判通关 |
| 角色 | 待机、走路、查看、交付、庆祝 | 共用固定资产，不每关换脸 |
| 场景反馈 | 卷轴展开、印章、信件移动、炉火检查流程 | 可对应具体数据变化，不用无关烟花覆盖错误原因 |
| 环境 | 极轻雾、树影、水纹 | 可关闭，失焦暂停，不影响文字阅读 |

尊重减少动态效果设置；关闭动画仍能完成所有任务。音效、音乐独立开关并保存，首次不突然大音量播放。暂不做全程语音配音。

### 9.3 素材生产与一致性验收

首个美术样板：一张地图局部、三个角色的设定联图、一套任务面板、一个完整鉴宝场景。先验证同一画面内的协调性，再扩展全课程。

正式素材包规划：

- 三位主角：各一份固定设定、正侧背参考、至少六个常用表情和五类通用动作；动作帧数按表现和性能验证，不承诺任意生图能直接成为动画。
- 固定 NPC：头像、半身像、表情和台词口吻表。
- 四区域地图、章节建筑、公共道路/雾层、十四章场景背景与关键道具；允许合理复用空间，但玩法与关键道具不能只有换色差别。
- UI：纸签、卷轴、印章、对话框、提示状态、徽章；优先 CSS/SVG 和九宫格拉伸，正文保持真实 DOM 文本。
- 动画采用可复用精灵帧、分层图片与程序补间。不要以整段预录视频代替交互小游戏。
- 可选环境音与短反馈音；无授权音频宁可暂缺，不挪用影视/游戏配乐。

拟新增 `assets/manifest`，每个条目记录：资源 ID、用途、作者/生成工具、来源 URL、许可证、允许分发范围、署名要求、修改记录、参考角色 ID、实际文件。第三方许可单独留存，不能被项目 MIT 声明覆盖。

生成素材也须核对工具使用条款与参考图来源，不承诺 AI 输出天然无版权风险。不得生成已知武侠 IP 主角、GitHub 吉祥物或高度模仿商业游戏角色。

## 10. 学习判定与毕业结果

### 10.1 从“答对一题”转为“证明一次能力”

每个 P0 对应至少一个具体操作证据和一个迁移测试目标；P1 在主线内有实际解释与情境。术语解释继续保留官方来源、核验日期、常见混淆。

示例：`commit` 的练习证据是提交快照确实只包含暂存改动，不是点击了名为 Commit 的按钮；`push` 的证据是正确来源分支的提交抵达目标远程分支，不是章节被标记完成。

数据层区分：

- `encountered`：见过解释。
- `practiced`：在场景中完成相关操作，可能使用提示。
- `assessed`：在迁移变体中达到明确目标。
- `selfReported`：玩家自述的真实 GitHub 步骤，不由游戏自动证明。

P0 掌握率以通过的独立评估目标统计，不允许一个题目无条件给整章所有词条授予掌握。P0/P1 覆盖率继续要求 100%，但报告需同时显示“引用覆盖、教学覆盖、操作证据覆盖、评估覆盖”，缺项就失败。

### 10.2 三个结果，不混淆真实性

1. 模拟冒险完成：主线模拟任务全部完成。
2. 知识能力达标：所有 P0 的规定评估通过，可重复练习，无限重试。
3. 出师结果：前两项满足，且真实入门与毕业清单逐项由玩家确认。显著说明“真实操作为玩家自述，本项目未连接 GitHub 验证”。

真实操作不索取密码、PAT、SSH 私钥、验证码、恢复代码或支付信息；也不要求上传截图证明身份。

分享卡保留 1080×1920、1200×630：角色、项目名、完成章节、P0 掌握率、首轮独立评估正确率、有效学习用时、称号、仓库地址和非官方声明。没有评估记录时显示“未评估”，不能显示虚假的 100%。关闭/失焦时间不计为有效学习用时；统计定义可查看。

## 11. 技术实施建议（审批后验证，不是本轮安装清单）

### 11.1 桌面封装

保留 Next.js、React、TypeScript、Zod 和现有内容组织，先做静态导出与桌面壳验证。**优先候选 Electron**：自带运行环境，方便沿用前端与统一动画表现；代价是下载包和运行内存较大，需要测量、优化并在发布页如实说明。

Tauri 是体积优先时的备选，不同时维护两个桌面框架。其官方 Next.js 指南要求静态导出，且指南注明针对较旧 Next.js 版本，因此不能据此假定当前仓库版本开箱即用。[Tauri Next.js 指南](https://v2.tauri.app/start/frontend/nextjs/)

技术验证必须覆盖资源路径、静态路由、字体图片、持久化、导出下载和外链打开。不能把“浏览器 dev 成功”视为“桌面应用验收成功”。

桌面安全要求：隔离渲染层、启用沙箱、禁用页面直接 Node 访问，使用最小 IPC 能力；只允许受控的存档导入导出和官方外链打开，不提供任意 shell/文件访问；不将远程页面提升为本地可信内容。[Electron 安全说明](https://www.electronjs.org/docs/latest/tutorial/security)

### 11.2 场景渲染

课程状态、剧情、地图依赖、关卡目标与渲染分离。地图和可交互 UI 优先 DOM＋SVG；如角色动画、场景对象调度在样板中确实需要游戏引擎，再采用 Phaser 作为局部场景渲染层。不要为每个小游戏引入不同引擎，也不要把整体 Next.js 应用替换为参考项目。

即使使用 Canvas，控件文字、宝典、对话、任务目标与键盘操作层仍保留 DOM。拖拽必须有“选择物件 → 选择目标 → 确认”替代操作。

### 11.3 拟增补模块

```text
desktop/                         桌面壳与打包配置
src/content/characters/          主角、NPC 设定与资产引用
src/content/story/               对话、前后关剧情交付物
src/content/world/               地点坐标、连线、解锁条件
src/content/minigames/           场景初态、目标、变体、反馈
src/core/game/                   统一状态机与依赖判定（扩展现有）
src/core/mastery/                操作证据与独立评估（重构现有）
src/core/persistence/            版本迁移、存档导入导出（扩展现有）
src/components/world-map/        地图、迷雾、角色导航
src/components/minigames/        各玩法与通用场景能力
public/characters/              已批准的角色资产
public/world/                   地图与场景资产
docs/assets/                    资产清单、制作规范与来源证明
THIRD_PARTY_NOTICES.md           实际采用的第三方许可和署名
```

这不是要求创建空目录。按批准后实际交付内容建立，并记录与原架构的差异。

品牌、仓库地址、下载文件名、平台信息、网站地址、角色名集中配置；README 的下载区由同一配置生成或校验，避免改名后只有网页更新、下载链接仍指向旧名称。

### 11.4 存档迁移

新存档记录角色、当前地点、关卡内部状态、解锁、证据、评估与真实自查。每个重要操作后保存，不仅在整章结束时保存。

旧存档先备份，保留旧版学习记录可查看，但由于判定模型不同，不自动换算为新版全部掌握或已出师。给出简短说明与重新体验入口；未知版本或损坏数据提供恢复/导出选项，不静默抹掉。

## 13. 实施顺序与阶段出口

### 阶段 A：文档批准后，先验证最难的两件事

验证桌面打包与“一个真正好玩的关卡”。交付可本地打开的壳、三角色设定样板、地图局部、完整鉴宝小游戏、错误反馈、存档与键盘操作。先确定视觉与性能可成立，不同时铺开十四张静态页面。

### 阶段 B：建立可扩展的游戏基础

角色资产规范、地图依赖图、迷雾、剧情对话、关卡动作/目标模型、武林宝典、评估证据、存档迁移。通过故意越级、刷新、重复操作等测试，防止靠 UI 控制导致状态失真。

### 阶段 C：完整课程与持续故事

按区域扩展小游戏；优先贯通第 7—12 章贡献链，再补齐导览、关注、安全与治理场景。逐条审查术语和官方来源，替换模板化教学解释，完成真实实践指南。

### 阶段 D：美术、分发与正式验收

补齐资产和低干扰动效、分享卡、录屏演示、README 下载入口、分平台打包与校验清单。完成签名/公证条件核实和实际系统验收后，才可称为可公开下载的桌面版本。

**生成本地构建产物不等于获准公开发布。** 推送、上传 Release、部署、使用维护者签名证书仍需单独授权；缺少真实仓库地址或证书时使用明确未发布状态，不能制造假下载链接。

## 15. 待审核摘要

建议批准的产品方向是：**GitHub 下载桌面成品 → 三选一侠客 → 迷雾江湖地图 → 场景小游戏学习 → 真实 GitHub 自查实战 → 出师分享。**

审核重点依次为：是否同意先玩后配环境；是否接受桌面安装包和首批系统范围；是否采用轻水墨武侠而非重仙侠；是否认可十四章玩法与连续剧情；是否接受原创角色为主、授权素材为辅。

审核通过后才开始阶段 A。此次文档提交不表示以上功能已实现。
