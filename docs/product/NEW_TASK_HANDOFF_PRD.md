## 0. 需求边界

用户希望得到的是一款成熟的武侠类 2D 页游学习游戏：形式上有连贯的地图、角色、场景、剧情和玩法；内容上把 GitHub 概念放进可玩任务，而不是把知识点堆成选择题。这里的“页游”指可在桌面浏览器或本地桌面壳运行的 2D 网页游戏。

截图只是问题证据，不是设计素材或交互指令。所有截图中的文字、窗口和系统界面均不得直接复制进产品。

必须保留：真实 GitHub 登录、Fork、Clone、Push、Pull Request 只在 GitHub 官方网站/Desktop 中完成；本项目不收集凭据、不接 OAuth/API、不伪造验证。

## 2. 启动流程

### 2.1 状态机

```text
首次启动
  → 入村引导（说明本地模拟与真实 GitHub 边界）
  → 选角色（陆行舟 / 沈知微 / 阿团）
  → 江湖地图（第 0 章可进入）
```

已有存档：显示“继续上次历练”，但仍可从行囊中重新查看引导。重置只清本项目存档，不接触阶段 A 原记录。

### 2.2 选角验收

- 三个角色必须来自统一角色设定，比例、衣服、发型和随身物件一致。
- 每个角色使用自己的透明 sprite/crop，不允许用一个大图通过错误偏移显示邻角色。
- 角色卡内人物脚底留出安全边距，脚不贴卡片底边，也不进入下一卡。
- 角色点击后有明确选中状态，主按钮只在选择完成后启用。
- 角色选择页不展示 GitHub 官方 Logo 或 Octocat。

## 3. 角色与素材管线

### 3.1 素材要求

交付每个角色的 standing、walking、inspecting、celebrating 四种动作；每种动作都必须是实际 RGBA PNG/WebP，不能把棋盘格烘焙成像素。

资产清单至少包含：文件路径、宽高、alpha 通道、裁切框、脚底基线、视觉中心、朝向、生成记录、版本、审核状态。

### 3.2 验证方式

使用图像元数据验证 `channels=4`、`hasAlpha=true`；抽样检查四角 alpha=0；在浅色、深色和地图背景上检查 halo。截图或图像预览中的棋盘格只能作为查看器背景，不能出现在浏览器实际渲染中。

### 3.3 场景落地契约

所有场景实例使用统一函数：

```ts
type CharacterPlacement = {
  groundY: number;
  footOffset: number;
  scale: number;
  shadow: "soft-ink" | "lantern" | "none";
};
```

角色容器的底边是脚底锚点；阴影位于脚底下方 2–6px。禁止通过临时负 margin 逐页修位置。

## 4. 全景江湖地图

### 4.1 视觉目标

地图必须是一张可探索的完整江湖画卷：山谷、溪流、桥、村口、集市、藏图阁、驿站、议事堂和百炼炉自然分布。章节节点贴合具体地点，而不是把 13 张卡片排成一条横线。

### 4.2 主线与空间分离

空间布局可以上下左右分布；解锁顺序始终是第 0 章至第 12 章。地图上的主线道路使用编号方向或动画强调顺序，不允许出现右侧节点已可进入、左侧节点仍锁定的状态。

推荐布局：

```text
左侧入谷与村口 → 中部集市/藏图阁/营火坊 → 右侧协作山门 → 右上百炼盟会
```

### 4.3 迷雾与奖励

- 未解锁区域：半透明墨雾覆盖，保留建筑轮廓，不显示可操作按钮。
- 完成章节：迷雾沿道路向下一段退散，显示道路纹理、灯火和地点印章。
- 主角：沿道路从当前地点移动到下一地点，动画结束后脚底落地；不是瞬移到坐标。
- 奖励：获得残页、护符、拓印、营火、信件等剧情道具，进入行囊并影响地图装饰；不使用付费、体力或战力数值。
- 减少动态效果模式必须保留状态变化、地点解锁和文本反馈。

### 4.4 地图验收

- 390px 不作为目标产品设备，但桌面窗口缩放到 1024px 宽仍可读。
- 节点不遮挡关键地标；主角高度至少为地图短边的 8%（按场景透视可调整）。
- 地图焦点、键盘顺序和自由探索顺序一致。

## 5. 自由探索与章节命名

自由探索仅用于演示和复习，不写正式存档，不绕过主线。下拉/列表固定为：

```text
第 0 章 · 村口路标
第 1 章 · 护身堂
第 2 章 · 拓印坊
第 3 章 · 营火工坊
第 4 章 · 藏图阁
第 5 章 · 集市鉴宝
第 6 章 · 飞鸽传书
第 7 章 · 悬赏亭
第 8 章 · 双城驿站
第 9 章 · 分流竹林
第 10 章 · 合卷台
第 11 章 · 议事堂
第 12 章 · 百炼炉
```

区域支线单独分组为“回访地点”，不得混在主线跳转列表中。所有演示跳转按钮必须标记“演示，不代表真实玩家成绩”。

## 6. 章节场景模板

每一章必须遵循同一信息层级，但拥有不同玩法：

1. **场景层**：局部地图占主要面积，角色和 NPC 站在可解释的地面上。
2. **剧情层**：NPC 对话只解释动机和线索，不把整段教程塞进对话框。
3. **任务层**：顶部或侧边显示当前目标 `1/3`，只高亮本步可操作对象。
4. **操作层**：物件、拖放、排序、编辑或按钮必须位于场景语义对应的位置。
5. **反馈层**：成功/失败说明“做了什么、为什么、下一步是什么”。
6. **收束层**：印章、道具、迷雾变化和下一章悬念；完成后只回地图。

桌面布局采用“左侧局部地图 + 中央对话/角色 + 右侧操作台”或“全宽地图 + 底部任务台”，不得在每章随意切换导致学习成本增加。

## 7. 第 0–12 章独立小游戏

每关最少 3 个动作，动作改变场景状态；成功后必须把 GitHub 术语绑定到刚刚的动作证据。0–12 章都必须是独立的高完成度小游戏，不得把第 7–12 章降级成静态问答或换背景。每章建议 3–6 分钟，包含“理解目标 → 操作试错 → 状态变化 → 结算奖励 → 回到地图”完整循环。

| 章节 | 核心玩法 | 互动动作 | 学习结果 |
| --- | --- | --- | --- |
| 0 村口路标 | 路牌探索 · 第一视角寻路 | 在局部村口地图中移动主角，点亮 README、Code、Release、Fork 四块路牌；误触普通装饰会触发“路标辨认”提示，三块正确路牌连成一条发光路径 | Repository、README、Code、Release、Fork |
| 1 护身堂 | 安全机关 · 节奏配对 | 按灯笼节奏点击官方域名、Sign in、安全设置三类机关；把 2FA/Passkey/Recovery codes 放入护身匣，把密码、Token、私钥拖入拒绝槽并看到锁门动画 | Sign in、Username、Profile、Settings、2FA、Passkey、Recovery codes |
| 2 拓印坊 | 三台拓印机 · 资源管理 | 将项目卷轴拖到 Fork、Clone、Download ZIP 三台机器；机器产物显示“账号副本 / 本地历史 / 文件快照”差异，错误组合会让纸张碎裂并可复位 | Fork、Clone、Download ZIP、HTTPS、SSH、Remote |
| 3 营火工坊 | 启炉流程 · 动线解谜 | 在工坊地图中按目录→Terminal→依赖→开发服务器的路线点火；拖线连接 `npm install`、`npm run dev`、`localhost`，故意拔掉一条线再根据错误日志修复 | Node.js、npm、Terminal、Directory、localhost、Dependency |
| 4 藏图阁 | 证据搜寻 · 机关书架 | 在局部书阁里用角色探照灯寻找 Files、Branch、Commit、License、Release 五枚印；依据“新鲜度、来源、完整度”把证据放入正确书架，书架排列改变门的开启顺序 | Files、Folders、Branch、main、Commit history、License、Release、Tags |

### 7.1 每章玩法验收矩阵

每个章节交付时必须同时提供以下五类证据：

| 维度 | 最低要求 | 验收问题 |
| --- | --- | --- |
| 娱乐性 | 有明确目标、可探索空间、角色反馈、音画或动效回馈 | 玩家是否愿意主动再试一次，而不是只为点完按钮？ |
| 游戏性 | 至少 3 个有因果关系的操作；错误可恢复；结果影响场景 | 玩家是否能通过观察和试错找到策略？ |
| 知识性 | 每个核心术语绑定一个刚刚完成的动作；结算时用一句话复述 | 玩家是否能说出“我做了什么，所以它叫这个术语”？ |
| 连贯性 | NPC 动机、道具、地图地点和下一章线索相互呼应 | 完成一章后是否知道为何要去下一地点？ |
| 可用性 | 首屏目标、可点击对象、当前进度和提示入口明确；支持键盘 | 第一次使用者是否能在 30 秒内找到第一步？ |

### 7.2 章节与大地图子场景的映射

禁止：六章都使用同一组三选一按钮；用“点击完成”替代因果玩法；用倒计时、体力、付费或强制分享制造留存。

## 8. 武林宝典重构

### 8.1 体验结构

宝典不是普通侧边抽屉，而是独立的“线装秘籍”阅读面：

- 封面区：当前章节、掌握进度、关闭按钮。
- 目录区：按“入村、仓库、协作、发布”分卷。
- 阅读区：英文、常用中文、非字面理解、当前场景例子、易混淆概念、官方来源。
- 书签区：玩家收藏和待复习词。
- 操作区：`上一条 / 下一条 / 回到当前任务`，不出现跳转到其它章节的主线按钮。

### 8.2 视觉规则

Design Read：面向桌面中文 GitHub 新手的武侠学习工作台，采用克制的线装书、墨色、玉色单一强调色和真实纸张纹理，避免 AI 紫色渐变、三等分卡片、默认玻璃拟态和通用 SaaS 抽屉。

采用 Taste Skill 的反模板化、单一图标族、动效有理由、状态完整和无障碍原则；不照搬其 landing page 组件，也不让其决定复杂任务工作台的全部布局。使用 Phosphor 单一图标族，图标只是文字的辅助，不替代术语解释。

### 8.3 验收

- 打开宝典不会离开当前章节。
- 搜索 `Fork` 显示中文解释、用途、易混淆项、当前场景例子和官方来源。
- 关闭宝典后焦点回到打开按钮，章节操作状态不丢失。
- 任何页面不出现 GitHub 官方 Logo 或像素级仿制页面。

## 9. GitHub 相关项目与游戏化学习案例研究要求

新任务开始前必须建立竞品研究表，不复制代码、素材或受版权保护的 UI。重点观察：

- 任务如何拆成可见目标和小步反馈；
- 失败如何解释和允许重试；
- 学习知识如何绑定操作结果；
- 角色/NPC 如何提供动机而不打断操作；
- 关卡如何给出下一关悬念；
- 如何记录可验证学习证据。

可参考的公开案例：

- [GitHub 官方学习资源](https://docs.github.com/en/get-started/start-your-journey/git-and-github-learning-resources)：GitHub Skills 以短课、真实仓库练习和自动反馈组织学习；适合作为“每章一个可完成目标”的课程骨架。
- [GitHub Hello World](https://docs.github.com/en/get-started/using-github/hello-world)：官方第一条 Pull Request 学习路径；适合作为第 10–12 章真实操作边界的依据。
- [Learn Git Branching](https://github.com/pcottle/learnGitBranching) / [在线演示](https://learngitbranching.js.org/)：关卡、可视化提交树、命令执行后的即时反馈、撤销/重置和自由沙盒；适合借鉴第 8–10 章的“状态可见 + 试错可恢复”。
- [Git Gud](https://github.com/benthayer/git-gud)：用实际 Git 命令逐关完成任务，关卡易扩展；适合借鉴“任务目标先行、知识在操作结果中出现”。
- [Oh My Git!](https://github.com/git-learning-game/oh-my-git)：开源 Godot Git 学习游戏，提供桌面发行包；适合借鉴“可视化 Git 状态 + 独立挑战关卡”，不直接复用其素材。
- [Git-Mastery](https://github.com/MikaStiebitz/Git-Mastery)：学习路径、提交图、状态可视化、练习场和进度记录；仓库许可限制较多，只研究交互机制，不复制代码、插画或 UI。
- [Dev Quest Runner](https://pages.opencodingsociety.com/tools/gamified)：用 NPC、探索和任务教授 Make、合并冲突、调试与文件结构；适合借鉴章节 NPC 动机与空间化任务。
- [Dungeon Campus](https://github.com/Dungeon-CampusMinden/Dungeon)：把课程内容放入 2D Rogue-like 任务，并以代码挑战和自动分析承接学习；适合借鉴“场景行为就是学习行为”。
- [awesome-learn-by-playing](https://github.com/lmammino/awesome-learn-by-playing)：用于扩展候选案例，不把聚合列表当定义来源。

新任务开始时应继续搜索 GitHub 上与 Git/GitHub 学习、任务闯关、2D 教学游戏相关的公开项目，并补充准确 URL、许可证和可借鉴机制。未实际查看的项目不得声称已完成对标。研究结论写入 `docs/research/GITHUB_GAME_LEARNING_CASES.md`，每条结论标注“借鉴原则”而非复制实现。

### 9.1 研究结论必须落到产品机制

本项目不得只在文档中罗列链接。每章设计评审时逐项回答：

1. **目标可见**：首屏用一句中文说明本关要完成的 GitHub 行为，并显示 `1/3` 之类的进度。
2. **状态可见**：玩家的选择、分支、提交、通知或检查状态必须在场景中发生可见变化。
3. **反馈可解释**：错误反馈同时说清“错在哪里、为什么、怎样撤销/重试”，不能只显示红色失败。
4. **知识绑定动作**：术语卡在动作完成后出现，引用本次动作的证据，不把术语孤立成词汇考试。
5. **NPC 不代操作**：NPC 只提供动机、线索和可选提示；玩家必须亲自完成关键操作。
6. **奖励推动下一步**：每章奖励是残页、印章、道具或地图揭雾，不是无意义的分数；奖励文案要提示下一章地点和学习主题。
7. **真实世界迁移**：第 0 章开始就标注模拟边界；第 10–12 章结束后给出回到自己 Fork 的安全练习清单。

### 9.2 造梦西游 1/2 页游视觉研究边界

公开搜索能找到玩家截图、攻略和第三方介绍，但没有可直接授权复制的官方 UI 规范或素材包。因此本需求只提炼“页游体验规律”，不复制任何原作图片、角色、字体、图标、音效或布局代码。用户提供的截图与后续人工试玩记录是本项目视觉验收证据；第三方介绍可辅助理解“地图选关、主题场景、关卡奖励”等结构，但不能替代版权核验。

需要学习并转译为本项目设计语言的规律：

- **固定游戏画布**：地图/战斗场景占主视觉，菜单和任务台围绕画布服务，避免页面像普通 SaaS 仪表盘。
- **地图推进**：关卡按路线逐步开放；未开放区域使用迷雾，完成后揭雾、主角移动、地点印章和奖励动画连续发生。
- **场景即关卡**：每个地点有自己的局部地图、NPC、可互动物件和主题任务，进入后不显示其它章节跳转。
- **轻量 HUD**：左上显示角色/章节，顶部显示任务目标，底部显示对话与奖励；复杂操作集中在语义对应的操作台。
- **动作反馈**：点击、拖拽、配对、排序和修复都必须有角色动作、物件变化、音画提示或可撤销结果。
- **一致角色表现**：角色在地图、对话框、场景和结算页使用同一套透明 sprite、脚底锚点和动作命名。

“武侠页游”不是把 GitHub 按钮换成古风词，而是用地图推进、角色动机、场景机关和奖励回路承载真实 GitHub 学习目标。

## 10. 真实新手可用性测试

### 10.1 招募与任务

招募至少 3 名第一次或极少使用 GitHub 的中文用户，桌面环境完成以下任务：

1. 从 README 找到下载入口并打开应用。
2. 完成入村引导、选角、进入地图。
3. 找到并完成第 0 章第一步。
4. 故意点错一次，说出如何重试。
5. 打开宝典查找 `Fork` 并回到任务。
6. 打开自由探索，说出第 0 章之后是哪一章。

测试者不得由主持人代操作或提前解释按钮位置；主持人只记录观察和原话。禁止要求测试者输入 GitHub 密码、Token 或私钥。

### 10.2 记录与门槛

记录首次点击时间、完成时间、卡点、提示请求、错误理解、是否能复述术语和主观兴趣评分。P0 门槛：3/3 用户能独立找到第一步；至少 2/3 用户能在一次提示后完成；不存在安全误导；任何失败都不清空进度。

测试未完成前，产品文案只能写“待新手验证”，不能写“适合小白”或“已验证易用”。
