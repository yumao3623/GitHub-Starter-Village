# 学习游戏、武侠视觉与素材复用研究

研究日期：2026-09-10  
用途：支持[武侠闯关改版需求评审](../product/WUXIA_REDESIGN_PRD.md)，不是依赖安装或素材导入清单。

## 1. 结论

可以参考成熟学习游戏的“操作改变状态、状态决定通关”，参考武侠项目的地图、人物和对话组织，以及图集/九宫格 UI 的生产方法。**本轮没有发现一套已经确认可整包复制、风格统一、覆盖三主角和全部课程场景的武侠资源包。**

建议采用“玩法借鉴＋少量许可清楚的组件改编＋原创人物与场景”。不要因仓库公开或某段代码是 MIT，就把商业游戏的图片、音乐、关卡文案一同搬进本项目。

范围说明：本轮阅读公开仓库 README、公开目录、许可证和作者文档；没有安装运行所有参考游戏，没有进行逐文件资产审计，也没有将第三方资源复制到本仓库。对性能、人物帧动画质量和素材完整性的判断仍需后续样板验证。下列“建议”是结合本项目需求作出的设计推论，不是参考作者的产品承诺。

## 2. 学习游戏：值得借鉴的是通关机制

### 2.1 Oh My Git!

来源：[项目仓库](https://github.com/git-learning-game/oh-my-git)、[许可证](https://github.com/git-learning-game/oh-my-git/blob/main/LICENSE.md)。

观察：提供桌面成品；使用 Godot 3，关卡定义拆分说明、初始 Git 状态和胜利检查，场景、图像、音效另行组织。仓库注明低维护状态，不宜当作最新工程模板。

建议借鉴：让玩家改变仓库状态后才完成任务；每关具备初态、动作、目标与反馈。用于本项目分支、远程同步和 PR 场景。

边界：项目采用 Blue Oak Model License 1.0.0，部分音效另有 CC0 来源。若未来复用，仍逐项保留许可；本项目不照搬 Godot 架构，也不让小游戏调用真实 Bash 操作玩家目录。

### 2.2 Learn Git Branching

来源：[项目仓库](https://github.com/pcottle/learnGitBranching)、[许可证](https://github.com/pcottle/learnGitBranching/blob/main/LICENSE.md)。

观察：输入操作后提交树动态变化，有沙盒、关卡、撤销和重置；关卡可用 JSON 表达。仓库标示 MIT。

建议借鉴：把 Commit、Branch、本地/远程位置画出来，目标检查独立于动效；“分流竹林”“双城驿站”可以同时展示操作前后差异。

边界：不是武侠美术包；其网页运行方式不代表当前 Next.js 项目可以直接双击 HTML。复用算法需要检查具体文件，不直接整站嵌入充当自有课程。

### 2.3 CodeCombat

来源：[仓库](https://github.com/codecombat/codecombat)、[关卡制作入口](https://github.com/codecombat/codecombat/wiki/Artisan-Home)、[作者许可说明](https://codecombat.com/legal)。

观察：围绕角色、场景实体、组件和关卡任务组织学习；适合参考“同一个英雄进入不同任务”。

许可分层：公开客户端代码 MIT；提供给关卡创作者的一般美术/音频等有 CC BY 4.0 授权；具体关卡及其专属内容保留权利。用户创建的素材还要遵守各自署名规则。

建议：借鉴角色与任务的组织方式，不复制关卡。即使一般资产许可允许，也需逐项确定来源并署名；其美术与本项目武侠方向不同，不建议直接拼贴。

## 3. 武侠项目：公开可见不等于能拿素材

### 3.1 jynew / 金庸群侠传 3D 重制版

来源：[项目仓库](https://github.com/jynew/jynew)、[项目许可证](https://github.com/jynew/jynew/blob/main/LICENSE)。

观察：可参考武侠世界的地点、NPC、对话和任务组织思路。

关键边界：LICENSE 对未获公开声明授权的代码与资源使用均有限制，部分目录还有补充协议。不能因名称含“开源”或源码可见就直接使用。

本项目决定：**仅作体验结构参考，不复制代码、人物、地图、音乐、剧情或商标资产。** 不使用已有武侠 IP 的角色替代自己的主角。

### 3.2 Miu2D

来源：[项目仓库与版权声明](https://github.com/luckyyyyy/miu2d)。

观察：采用 Rust、TypeScript、React、Canvas，提供 NPC 状态与 GUI/游戏逻辑分离的参考；说明 Web 技术可以承担二维 RPG 场景。

边界：仓库区分 MIT 引擎代码与原游戏图片、音频、地图、脚本等，后者权利归相应权利人，不随引擎 MIT 开放。

建议：研究 React 与场景对象的职责边界；不下载其商业游戏资源，也不为了几个动画引入整套引擎。

## 4. UI、山水和通用资源：有条件的候选

### 4.1 Xianxia UI

来源：[仓库与组件说明](https://github.com/rainlotus97/xianxia-ui)、[LICENSE](https://github.com/rainlotus97/xianxia-ui/blob/main/LICENSE)。

观察：Vue 3 组件以图集、坐标配置、裁图和九宫格拉伸组织边框；也有 CSS/SVG 线条界面、任务条和头像框。

建议：借鉴“边框装饰是资产，文字和行为仍是组件”的办法。适合纸签、卷轴框、角色框，不把整张按钮连文字烘焙成图片。实际可考虑构建时裁图，减少运行时处理。

许可注意：LICENSE 是 MIT，但 README 末尾还出现 ISC 字样，文档存在不一致。导入前需核对选定版本和文件声明；图集原始出处仍须单独确认。当前只列为**待核实改编候选**，不宣称整包资产已获审计。

不采用其修炼货币、倒计时和资源数值玩法，也不为复用组件在 React 应用内加入完整 Vue 运行栈。

### 4.2 Shan Shui / shan-shui-inf

来源：[项目](https://github.com/LingDong-/shan-shui-inf)、[许可证](https://github.com/LingDong-/shan-shui-inf/blob/master/LICENSE)。

观察：用程序生成中国山水画，采用浏览器图形表达；许可证为 MIT。

建议：可研究山石轮廓、树木与远近层次，必要时按许可改编局部生成逻辑，保留版权说明。

边界：连续山水背景不是可玩的任务地图。本项目地点、路桥、路径与先修关系必须人工编排，不能用随机山水替代地图设计；不因采用背景生成器而承诺有人物和建筑素材。

### 4.3 Kenney · UI Pack (RPG Expansion)

来源：[作者资源页](https://kenney.nl/assets/ui-pack-rpg-expansion)。

观察：作者页面标明 CC0 的 RPG 通用 UI 资源包。

建议：适合作为原型控件资产候选或通用基础元素来源，正式采用时保存资源包内许可与来源记录。它不是专门的中国武侠人物/地图包，不应把“可免费使用”作为风格合适的证明。

## 5. 动画实现参考与隐私检查

### Phaser 官方 React 模板

来源：[phaserjs/template-react](https://github.com/phaserjs/template-react)。

观察：模板描述 React 与游戏场景间的桥接、事件通信、场景加载和静态资源组织；可作为局部场景渲染方案参考。

需要注意：README 标明模板的统计脚本会发送模板/构建等信息，并指出示例品牌美术并非随代码自由授权。即便不包含个人信息，也不符合本项目默认无遥测的要求。

建议：若采用相关实现，先核对版本和逐文件许可；不引入统计脚本、示例 Logo 或角色。保留 React 处理可访问界面和学习状态，场景层只负责呈现、输入与动画。先证明 DOM/SVG 不足以满足样板需求，再引入引擎。

## 6. 下载与桌面分发依据

| 来源 | 已确认的内容 | 对本项目的影响 |
| --- | --- | --- |
| [GitHub：链接到 Release](https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases) | 支持 latest Release 和指定资产名的最新下载链接 | README 可放直达成品的分系统按钮；资产命名与上传完整性需发布流程保证 |
| [Electron：应用分发](https://www.electronjs.org/docs/latest/tutorial/application-distribution) | 桌面分发需要打包，并考虑签名等环节 | 不能把源码 ZIP 当桌面应用，也不能承诺未经签名的包在所有电脑无提示打开 |
| [Electron：安全](https://www.electronjs.org/docs/latest/tutorial/security) | 桌面 Web 内容需要严格隔离和受控能力 | 禁止远程页面访问本地高权限能力，避免任意命令执行 |
| [Tauri：Next.js 集成](https://v2.tauri.app/start/frontend/nextjs/) | 推荐静态导出；指南适用版本说明较旧 | 当前 Next.js 版本需要单独验证，不把教程存在等同兼容性结论 |
| [Tauri：分发](https://v2.tauri.app/distribute/) | 分平台构建、签名、公证各有要求 | 证书、账号和真实系统验收是发布条件，不是仅写配置即可完成 |

工程建议属于方案推论：先验证 Electron 成品体验，再决定是否需要以 Tauri 换取更小包体。不要为了避免产品选择而同时维护两套壳。

## 7. 素材采用流程

1. 定位原作者仓库或资源页，而不是只保存搜索结果、转载下载站或截图。
2. 阅读项目 LICENSE、资源目录补充声明、单文件说明；记录选定版本/提交与来源时间。
3. 分别确定代码、图片、字体、音频、角色/IP 和关卡文案的权利，不把它们视为同一个许可对象。
4. 标记状态：可采用、附条件可采用、待核实、禁止采用。待核实内容不进入正式包。
5. 保存原始许可证与署名，记录改动；需要原作者额外许可时先获得许可，不能靠“非商业学习项目”自动豁免。
6. 统一调色、尺寸、轮廓与动效后再纳入品牌；来源不同不意味着可以忽略风格一致性。
7. 构建时检查资源清单，确保正式包与开源仓库均携带必要说明。

生成素材采用相同的可追溯原则：记录工具、参考图及其许可、生成/编辑过程和输出文件；核心人物先确定参考表，再产生动作和表情。角色一致性验收看实际图，不仅看提示词是否重复。

## 8. 审核后最值得先验证的三个样板

1. **桌面成品样板：**无 Node/Git 的干净目标系统，下载、安装、打开、断网运行、保存和重新打开。
2. **美术一致性样板：**三个角色的同尺度设定图＋地图局部＋鉴宝场景，验证角色在头像、站姿、动作间一致。
3. **玩法样板：**集市鉴宝的证据收集、条件匹配、错误反馈、复玩变体和地图解锁；证明它不是带动画的选择题。

这些样板尚未制作。本轮交付仅为研究结论及需求文档，等待用户审核。
